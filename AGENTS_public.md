# Public agent guide for AsyncBEV

Use this guide when reading, explaining, or changing this repository. Start with the [README](README.md) for installation, data preparation, available assets, and training/evaluation commands.

`AGENTS_public.md` is an explicit public guide, not a universally auto-discovered filename. When starting an AI coding assistant on a fresh clone, ask it to **read `AGENTS_public.md` before working**, or configure the assistant to load it. All paths below are relative to the repository root.

## Project scope and reading order

This repository contains the **CMT implementation of AsyncBEV** for asynchronous camera/LiDAR 3D object detection on nuScenes. It supplies model plugins, data pipelines, configurations, and evaluation extensions. The paper's UniBEV implementation is outside this repository.

The [ICLR 2026 poster](assets/AsyncBEV_ICLR26_poster_resize.png) provides a visual overview of the paper. Use the source and configuration guidance below to establish what this repository implements.

1. Read the README's release status and environment requirements. Training/evaluation tools are bundled; the compatible MMDetection3D environment and external data/checkpoints remain prerequisites.
2. Select a configuration in [projects/CMT/configs](projects/CMT/configs). Inspect its `plugin_dir`, `model`, `train_pipeline`, `test_pipeline`, and `data` definitions before tracing or changing code.
3. Follow the registered dataset, pipeline, detector, and head classes below. Trace the actual imports: similar filenames do not necessarily identify the active implementation.

A useful training trace is: configuration → dataset/pipeline → `CmtDetector.forward_train` / `forward_pts_train` → `CmtHead.forward_single` and temporal alignment → detection and flow losses. For inference, follow `CmtDetector.simple_test` / `simple_test_pts`, then the chosen evaluator. Trace the alignment outputs into their callers rather than assuming the method simply resamples raw sensor tensors.

For a concrete starting configuration, use [cmt_asyncbev_lidar.py](projects/CMT/configs/fusion/cmt_asyncbev_lidar.py). The camera and FD configs preserve the main 12-epoch, `2e-5`, four-samples-per-GPU settings. FD is named for the paper's frozen detector and uses the same LiDAR inference configs with its own checkpoint. Choose variants according to their actual settings and checkpoint provenance, not just filename similarity; the retained baseline schedules are not independently verified historical run reconstructions.

## Compatibility and scientific conventions

- Preserve the README's CMT-compatible environment, including **MMDetection3D 1.0.0rc5**, MMCV 1.x runners, and MMDetection registries. A migration to MMEngine or a newer framework is a separate change that needs validation.
- Apply [requirements/model-constraints.txt](requirements/model-constraints.txt) to model-environment installs: NumPy `<1.24` preserves legacy sampling aliases and YAPF `0.40.1` preserves MMCV config formatting. This is a compatibility constraint file, not a complete tested dependency lock; the separate CPU flow environment uses its own NumPy 1.x guidance.
- Synchronous `fusion/cmt.py` training additionally requires the remapped image-backbone initialization and a CMT GT database with point/image crops and `nuscenes_dbinfos_train.pkl`; see [data preparation](README.md#data-preparation). Main AsyncBEV/FD configs disable database sampling and use full CMT detector initialization.
- Keep **FlashAttention 0.2.2**, which matches the plugin's `flash_attn_unpadded_kvpacked_func` API. The bundled [wheel](wheels/README.md) targets CPython 3.8 / PyTorch 1.11.0 / CUDA 11.3 / Linux x86_64; it is separate from the README's upstream CMT PyTorch 1.9.0 / CUDA 11.1 source-build example. Check the binary target and SHA-256 before installation; copying the wheel does not establish a passing GPU runtime test.
- Configurations are executable Python. Values such as `data_root` and `eval_async_frame` are embedded into nested pipeline dictionaries when the config is constructed. Changing a top-level value afterward may leave the effective loader settings unchanged; inspect the resolved nested values.
- Use sensor timestamps and loader logic to establish delay. In the documented maximum-delay configurations, `eval_async_frame=-1` selects the last available history entry; a filename suffix alone does not establish the actual time offset.
- `LoadAsyncPointsFromMultiSweeps(sensor_staleness_feats=True)` measures the fifth point channel's time offsets in seconds relative to the synchronized sample, independently of spatial early motion compensation. Both options together shift the time reference once. Keep the default `False` behavior for existing AsyncBEV configs.
- Preserve time units, coordinate frames, and flow direction across loaders, metadata, alignment, and losses. The velocity-based alignment branch forms displacement by multiplying predicted velocity by `delta_t`; velocity and displacement are not interchangeable. Check source definitions before documenting tensor shapes or changing these conventions.
- The released asynchronous test pipelines also load flow labels, and the head's forward path accesses flow metadata. These are validation/prediction configs, not label-free deployment configs. Removing flow supervision from training does not by itself remove evaluation-time data dependencies.
- GT-flow generation/repair CLIs are bundled in `tools/data_converter`; use the standalone CMT geometry module to avoid importing detector dependencies. They require NumPy, nuScenes-devkit, pyquaternion and SDK dependencies, plus matching metadata and a trusted camera/LiDAR map. They do not generate the two custom maps. Preserve original normalized-grid endpoints/order, overlapping-box duplicate rows, no-box dummy behavior, camera CAM_BACK_LEFT timing, and source LiDAR extrinsics at the target camera ego pose. `resolution=0.5` is a historical grid parameter, not physical 0.5 m XY spacing.
- Generation creates new labels with all required fields. Repair defaults to read-only checking; `--apply` requires a separate, nonoverlapping output tree and preserves source labels/flow/extra metadata. Validate point rows against recomputed scene/pose flow, not shapes alone. `--existing validate` checks destination compatibility without overwriting; malformed files are errors. Do not add implicit in-place writes, bypass geometry mismatch checks, or infer release execution provenance from a successful synthetic test. Use small explicit selections and reports before any separately authorized dataset run.
- Use NumPy 1.x to produce pickles for the legacy CMT readers; NumPy 2.x module names can break their deserialization, so the tools reject new serialization under that version. New labels use protocol 4, while complete repair copies preserve original bytes. Keep array/schema compatibility separate from flow-value correctness.
- For grid-flow labels, `pts_in_boxes` stores generated point coordinates in the synchronized LiDAR frame, with rows aligned to flow arrays. It is a custom serialized field, not a missing point-in-box operator or a raw nuScenes field. Direct inspection of 30 camera-label PKLs from three published archives found the required field and matching finite point/flow arrays; keep this sampled data result distinct from the historical writer omission and from full-dataset validation. Reuse the upstream nuScenes converter's sweep enumeration/transforms when adapting the AsyncBEV map schema; distinguish standard info-file sweeps from the custom map layout.
- The AsyncBEV supplements are available on Hugging Face; use the README's verified release revision and linked dataset card for download and extraction. The distribution contains 512 independent `.tar.zst` flow archives plus four index/map pickle files, with a manifest and SHA-256 checksums. Extraction must restore `async_supplement/` under the nuScenes root; the compressed archive layout is not the loader's input layout. Pin the dataset revision and preserve checksum information when documenting experiments.
- The three confirmed trained checkpoints are available through three public read-only SURFdrive file links in the README's [checkpoint guide](README.md#checkpoints): main LiDAR epoch12, FD epoch10, camera epoch12. No login or password is required for these file links. The public checkpoint manifest and SHA256SUMS are under `assets/checkpoints/`. They are separate from the published Hugging Face data revision, which does not include these weights. Preserve checkpoint bytes when renaming, keep a separate checkpoint manifest/SHA256SUMS, and verify integrity against the sources. FD shares the LiDAR inference configs and retains the documented paper-metric discrepancies. Source-to-local byte identity and completed browser uploads were checked. Anonymous share pages and download endpoints returned HTTP 200 with the expected filenames and exact sizes; a full cloud download/hash comparison and model loading were not performed.
- Ordinary `--eval bbox` results and the custom all/static/dynamic breakdown are different evaluation paths. The latter uses `CustomNuScenesDataset.evaluate_dynamic`; see the README for its command-line availability and the **0.2 m/s** static/dynamic split.
- Use `tools/test.py --eval-dynamic` for the custom breakdown. Preserve its independent velocity-based prediction/ground-truth subsets. Evaluation saves the resolved config, invocation settings, predictions in nuScenes format, and metrics under a persistent output directory; do not merge results from different runs.
- For fresh training, `--no-resume` clears inherited resume settings but preserves `load_from` initialization. Resume flags are mutually exclusive. `--autoscale-lr` is optional and uses total distributed world size / 8; it does not reproduce a schedule after arbitrary batch-size changes.
- Keep paper-reported values, existing saved results, and newly measured results distinguishable. Compare metrics only after checking the data split, modality delay, checkpoint, configuration, and object subset. Do not infer protocol equivalence from matching rounded numbers.

## Working on the repository

- Keep the existing CMT implementation and framework baseline as the primary codebase. Consult other implementations only to recover missing helper functions or command-line entrypoints; do not bulk-import another model repository, its configurations, or its framework fork as part of that work. Reuse functionality already present here.
- Follow the surrounding Python/config style and keep changes focused. Preserve registry names, plugin imports, and the metadata fields consumed downstream unless intentionally changing their interfaces.
- For a pipeline or configuration change, inspect both training and evaluation consumers. For a model change, inspect the corresponding loss, freezing policy, and checkpoint compatibility.
- Use the README as the authoritative command reference. Before running, verify the bundled tools, pinned environment, nuScenes supplements, and a matching checkpoint. Launchers must preserve the caller's GPU visibility and resource settings. Config names and experiment IDs are machine-independent; use your own data paths, output directory, and logging settings. Training defaults to no resume, and inference takes its checkpoint from the CLI.
- Keep machine-local instructions, private discussion history, and internal audit records out of this public guide. The public guide must remain useful without access to a maintainer's local files.

## Validation and reporting

The lightweight regression suite runs with `python -m unittest discover -s tests -v` in the NumPy 1.x environment. It uses synthetic inputs and dependency stubs for orchestration, point loading, flow geometry, map resolution, and file creation/repair. It does not build the detector or run CUDA. There is no full experiment CI; passing these tests is not experiment reproduction.

With nuScenes SDK dependencies available, `ASYNCBEV_RUN_SDK_TESTS=1 python -m unittest discover -s tests -p test_flow_sdk.py -v` checks the real SDK and serial/parallel CLIs against temporary synthetic metadata. It does not read existing datasets or validate the full published release.

- For documentation changes, verify relative links and named source symbols, and run `git diff --check`. Also inspect newly created files, which are not included in an unstaged Git diff until tracked.
- For Python changes, check the changed files' syntax without importing the CUDA-dependent plugin, then run the smallest relevant behavioral check when its dependencies and data are available.
- For config curation, compare resolved model, data/pipelines, optimization, and schedule settings against the retained sources. Verify effective nested delay values, FD architecture compatibility, unique output names, and the absence of stale resume paths. Main inference coverage is LiDAR `0/5/10` and camera `0/3/7`; the compact set omits full baseline sweeps and ablations. Static config comparison does not establish a successful checkpoint load or reproduced metrics.
- For tool changes, run the regression suite and `bash -n tools/dist_train.sh tools/dist_test.sh`. Check ordinary and dynamic evaluator dispatch, distributed argument forwarding, resume policy, and preservation of GPU selection where affected.
- For training or evaluation changes, use the appropriate README procedure and record the configuration, checkpoint, split, actual delay, metric subset, command, and output location. Follow the execution environment's resource and job-management instructions.
- State what was actually checked and which runtime checks remain unrun, including missing prerequisites. Document genuine validation gaps rather than claiming success from an unavailable command.
